Student App: Project Guide

A Spring Boot REST API for students and courses. Login uses a JWT stored in an HttpOnly cookie, access is controlled by three roles (ADMIN, HR, EMPLOYEE), and the data is kept in SQLite.

1. Overview

This application manages students, users, courses, and tech stacks through a REST API. Users log in, and what they may do depends on their role. Data is saved in one SQLite file, student.db.

Main features

  • Register, log in, log out, and see the current user.
  • Three roles, with the rules in section 5. Admins manage users.
  • Create, list, read, update, and delete students. Link a student to an employee account.
  • Manage courses, tech stacks, and the links between them and students.
  • Consistent JSON responses and error codes.

Rule of thumb: each package has one job. Controllers handle HTTP, services hold the rules, repositories talk to the database, and mappers convert between shapes. Code only calls the layer directly below it.

3. How a request flows

Here is a create student request from an ADMIN:

Client sends JSON + cookie→ Security filters: token, then role rule→ Controller→ Validation (@Valid)→ Service (transaction)→ Mapper→ Repository→ SQLite

The response goes back the same way, as a DTO wrapped in ApiResponse:

Entity from database→ Mapper→ Response DTO→ ApiResponse wrapper→ Jackson turns it into JSON

Step by step

  1. Token check: the security filter reads the access_token cookie and verifies the JWT signature and expiry. If that fails, the request stops with 401.
  2. Role check: the token's role claim becomes an authority such as ROLE_ADMIN. The URL rules in SecurityConfig decide whether that role may call this path. If not, the request stops with 403.
  3. Method check: for GET /students/{id}, a @PreAuthorize rule runs next. It lets an employee through only if they own the student.
  4. Dispatcher finds the controller method that matches the URL and HTTP method.
  5. Jackson converts the JSON body into a request DTO record.
  6. @Valid checks the rules on the DTO. A failure becomes a 400.
  7. Service runs inside a transaction and calls the mapper and repository.
  8. Repository saves or loads the entity. Hibernate writes SQL to SQLite.
  9. Response is converted to a DTO, wrapped in ApiResponse, and written as JSON.

4. The layers

Entity: entity/

An entity is a Java class that maps to a database table. Each field is a column, and each object is a row.

ClassTablePurpose
AppUserapp_usersLogin accounts, with a password hash and a role
StudentstudentsStudent records, with an optional owner (an AppUser)
CoursecoursesCourses, with links to tech stacks and students
TechStacktech_stacksTechnologies such as Java or React
Role(stored as text in app_users.role)The enum ADMIN, HR, EMPLOYEE
AnnotationWhat it does
@Entity, @TableMarks the class as a table mapping and sets the table name
@Id, @GeneratedValue(IDENTITY)Primary key that the database assigns
@Column(nullable = false, unique = true)Required column, and a database rule that no two rows share the value
@Enumerated(STRING)Stores the enum name (ADMIN) instead of a number
@ColumnDefaultDefault value for existing rows when a column is added (used for role)
@ManyToOneMany students can point to one owner user
@ManyToMany with @JoinTableCourse links to tech stacks and students, stored in mapping tables
@PrePersist, @PreUpdateSet createdAt and updatedAt in UTC, and default the role to EMPLOYEE

Entities are never returned from the API. The controllers return DTOs. The entity has no setId(), because the database owns the ID.

Repository: repository/

A repository is an interface. Spring Data writes the implementation at startup.

  • StudentRepository: adds findByOwnerId, used when a user is deleted.
  • AppUserRepository: findByUsername, existsByUsername, and existsByUsernameAndIdNot (checks a rename does not clash with another user).
  • CourseRepository: findByStudentsId and findByTechStacksId. These search through the mapping tables, and they let a delete clean up links.
  • TechStackRepository: name checks for uniqueness.

DTO: dto/

A DTO (Data Transfer Object) is the shape of data the API accepts or returns. It is separate from the entity, so the database can change without breaking clients. They are Java records: immutable classes with generated constructors and accessors.

  • StudentRequestDTO, StudentResponseDTO: student input and output. The response includes ownerUserId.
  • CreateUserRequestDTO, UpdateUserRequestDTO: admin input for users. The update password is optional.
  • UserResponseDTO: id, username, role. Never the password.
  • CourseRequestDTO, CourseResponseDTO, TechStackRequestDTO, TechStackResponseDTO.
  • AssignOwnerRequestDTO: the body that links a student to a user.
  • AuthRequestDTO: username and password for register and login.
  • ApiResponse<T>: the wrapper for every response.

Mapper: mapper/

Mappers copy fields between DTOs and entities. StudentMapper, UserMapper, CourseMapper, and TechStackMapper are each a @Component with no dependencies. The course mapper reads the lazy collections, so it must run inside a transaction.

Service: service/

  • AuthService: registration (always EMPLOYEE), login, and token creation. The token includes the role.
  • StudentService: student CRUD, owner assignment, and removing a student from courses on delete.
  • UserService: admin user management. Deleting a user unlinks their students first.
  • CourseService: course CRUD and linking tech stacks and students.
  • TechStackService: tech-stack CRUD. Deleting one removes it from every course.
  • Dependencies arrive through the constructor, as private final fields. Writes use @Transactional. Reads use readOnly = true.

Controller: controller/

Controllers map URLs to methods and set the status code. They contain no rules beyond passing input to the service and returning its output. StudentController also carries the @PreAuthorize annotation on GET /{id}.

Exception handling: exception/

GlobalExceptionHandler is a @RestControllerAdvice. It turns exceptions into the same ApiResponse shape. Notably, AccessDeniedException becomes 403 (without this, the catch-all would return 500). Stack traces go to the log only.

5. Roles and permissions

Each user has one role. The role is written into the login token, and the security rules check it on every request.

RoleMeaningCanCannot
ADMIN Full access Everything: students, users, courses, tech stacks, links, owner assignment Nothing is blocked
HR Read-only access to students List all students, read any student by ID, see own profile Create, update, or delete students. Anything about users, courses, or tech stacks.
EMPLOYEE Access to own records only Read a student by ID when the student is linked to their account. See own profile. List all students. Read another user's student. Anything about users, courses, or tech stacks.

How the rules are enforced

  1. URL rules in SecurityConfig decide by path and method, for example GET /api/v1/students needs ADMIN or HR. This is easy to audit in one place.
  2. Method rules (@PreAuthorize) add checks that depend on the data. GET /students/{id} uses hasAnyRole('ADMIN','HR') or @studentAccess.isOwner(#id, authentication).
  3. Ownership: StudentAccess.isOwner compares the student's owner username with the logged-in username. A missing student counts as "not owned", so an employee gets 403 instead of learning which IDs exist.
A role change takes effect at the next login. The role is stored in the token. A user whose role was changed keeps the old role until the token expires (30 minutes) or they log in again.
Why the URL rule and the method rule both exist: the URL rule is a fast, simple gate. The method rule runs after the controller is chosen, so it can read the student and check the owner. Using both keeps the simple rules visible in one file and the data-dependent rule next to the code that needs it.

6. Login and the cookie

This section explains how a login becomes a cookie, and how that cookie is checked on each request.

The token

A JWT is three Base64 parts separated by dots: header.payload.signature.

  • Header: the algorithm, RS256.
  • Payload (claims): iss (issuer, "student-app"), sub (the username), iat (issued at), exp (expiry, 30 minutes later), and role (ADMIN, HR, or EMPLOYEE).
  • Signature: made with the RSA private key. Anyone can read the payload. Only the server can create a valid signature.

Login, step by step

POST /login→ Find user→ Check BCrypt hash→ Sign JWT with role→ Set-Cookie header
  1. The client sends username and password.
  2. AuthService.login loads the user. An unknown username throws InvalidCredentialsException.
  3. passwordEncoder.matches checks the password against the stored BCrypt hash. A wrong password throws the same exception.
  4. generateToken builds the claims, including role, and signs them.
  5. AuthController.login puts the token in the Set-Cookie header.
  6. The JSON body contains no token, only data: null.

Every later request, step by step

Browser sends cookie→ Read access_token→ Verify signature and expiry→ role claim becomes ROLE_*→ URL and method rules
  1. The browser sends the cookie automatically.
  2. resolveTokenFromCookie finds the access_token value. This replaces the default, which reads the Authorization header.
  3. The JwtDecoder checks the RS256 signature, then the expiry.
  4. The converter reads the role claim and grants ROLE_ADMIN, ROLE_HR, or ROLE_EMPLOYEE.
  5. If the token is missing or invalid, the entry point returns 401. If the role is not allowed, the access-denied handler returns 403.

Logout

Logout sends a cookie with an empty value and Max-Age=0. The browser deletes it. The server keeps no session, so a copied token still works until it expires.

7. ResponseCookie explained

This is the code that builds the login cookie, from AuthController.java:

private ResponseCookie buildCookie(String value, Duration maxAge) {
    return ResponseCookie.from(SecurityConfig.AUTH_COOKIE_NAME, value)
            .httpOnly(true)
            .secure(jwtProperties.cookieSecure())
            .sameSite("Strict")
            .path("/")
            .maxAge(maxAge)
            .build();
}

What ResponseCookie is

ResponseCookie is a Spring class that builds a Set-Cookie header. The standard jakarta.servlet.http.Cookie class cannot set SameSite, so Spring provides this builder. Calling .toString() produces the header text, which the login method sends with HttpHeaders.SET_COOKIE.

For a login, the header looks like this:

Set-Cookie: access_token=eyJhbGciOiJSUzI1NiJ9...; Max-Age=1800; Expires=...; Path=/; HttpOnly; Secure; SameSite=Strict

Each setting

Method callHeader outputWhat it doesWhy it matters
from(name, value)access_token=... Sets the cookie name and value The value is the signed JWT
httpOnly(true)HttpOnly Hides the cookie from JavaScript An injected script (XSS) cannot read the token
secure(...)Secure Sent only over HTTPS The token never travels unencrypted. Controlled by app.jwt.cookie-secure.
sameSite("Strict")SameSite=Strict Not sent on requests started from another site Main protection against CSRF. This is why CSRF tokens are turned off.
path("/")Path=/ Sent to every URL on the site All API endpoints need it
maxAge(duration)Max-Age=1800 Lifetime in seconds Matches the token's expiry. Logout uses Duration.ZERO, giving Max-Age=0, which deletes the cookie.
Why a cookie instead of localStorage? Any script on the page can read localStorage. An HttpOnly cookie cannot be read by JavaScript at all.
Local HTTP testing: the Secure flag means browsers and Postman drop the cookie over plain http://. Start the app with --app.jwt.cookie-secure=false for local testing. Production keeps it true and uses HTTPS.

9. Courses and mapping tables

A course can teach several tech stacks and can have several enrolled students. Each of these two relationships is many-to-many, so each has a mapping table with one row per pair.

courses←→ course_tech_stack←→ tech_stacks
courses←→ course_student←→ students

How the code maps them

@ManyToMany
@JoinTable(
        name = "course_tech_stack",
        joinColumns = @JoinColumn(name = "course_id"),
        inverseJoinColumns = @JoinColumn(name = "tech_stack_id"))
private Set<TechStack> techStacks = new LinkedHashSet<>();
  • @ManyToMany with @JoinTable creates the mapping table and its rows.
  • Course is the owning side. Adding to its set writes a row. Removing from the set deletes the row.
  • Sets ignore duplicates, so linking the same tech stack twice changes nothing.

Keeping the mapping tables clean

SQLite does not enforce foreign keys here, so deleting a row would leave dangling mapping rows. The services remove them:

ActionWhat the service does first
Delete a studentRemoves the student from every course (course_student)
Delete a tech stackRemoves it from every course (course_tech_stack)
Delete a userUnlinks that user's students (students.owner_user_id set to null)
Delete a courseNothing extra. Hibernate removes the course's own mapping rows.

Command-line values override the file, so you don't need to edit the file to test locally.

Upgrading an existing database

With ddl-auto=update, the first start after this change adds the new column and tables:

  • app_users.role is added with the default 'EMPLOYEE', so existing users become employees.
  • students.owner_user_id is added as empty, so existing students have no owner until an admin links them.
  • The three mapping tables and the two new tables are created.
  • Existing rows are kept.

Notes on SQLite

  • IDs: IDENTITY maps to SQLite's INTEGER PRIMARY KEY. An ID can be reused after the highest-numbered row is deleted.
  • Timestamps: stored as epoch milliseconds, because SQLite has no datetime type. In DB Browser: SELECT datetime(created_at/1000, 'unixepoch') FROM students;
  • Foreign keys: Hibernate does not create them for SQLite here, and SQLite does not enforce them by default. The services clean up links instead (section 9).
  • One writer: with one connection, concurrent writes queue up instead of failing with "database is locked".

Real database vs test database

Tests never touch student.db. You can confirm this by comparing the file's checksum before and after mvn test.

13. Errors

Every error has the same body shape, with success: false and a stable errorCode.

StatuserrorCodeCause
400VALIDATION_ERRORA field broke a rule. The message lists each field.
400MALFORMED_REQUESTBody is missing or not valid JSON
400INVALID_PARAMETERPath value has the wrong type, such as /students/abc
401UNAUTHORIZEDNo cookie, expired token, or tampered token
401INVALID_CREDENTIALSWrong username or password
403FORBIDDENLogged in, but this role may not do it, or an employee asked for a student they do not own
404STUDENT_NOT_FOUND, USER_NOT_FOUND, COURSE_NOT_FOUND, TECH_STACK_NOT_FOUNDThe record does not exist
409USERNAME_TAKENUsername already registered
409NAME_TAKENCourse or tech-stack name already used
500INTERNAL_ERRORUnexpected server error. Details are in the log only.
401 vs 403: 401 means the server does not know who you are. 403 means it knows who you are, but your role does not allow the action.
Why the same message for a wrong username and a wrong password? Different messages would let an attacker find which usernames exist. Both return "Invalid username or password".

How the test users are made

TestUsers creates a user with the role a test needs, then logs in through the real /api/v1/auth/login. Each test class sets up the users it needs, so the role rules are tested against real tokens.

Earlier bug caught by the tests: the first run failed with "Jwt and Opaque Token are the only supported formats". The fix was .jwt(...) on the resource server, so Spring knows the tokens are JWTs. Tests found it before any user did.
Another caught before release: the seeded HR username hr is shorter than the 3-character minimum. The first live run showed hr could not log in. The account is now hr_user.

15. Running it

  1. Install Java 21 and point JAVA_HOME at the JDK.
  2. Set the three seed passwords, each at least 8 characters. 
    SEED_ADMIN_PASSWORD=AdminPass123
SEED_HR_PASSWORD=HrPass1234
SEED_EMPLOYEE_PASSWORD=EmpPass1234
  3. Start the app from the project folder: 
    mvn spring-boot:run -Dspring-boot.run.arguments="--app.jwt.cookie-secure=false"
  4. The API is at http://localhost:8080/api/v1. Use --server.port=XXXX if 8080 is in use.
  5. Run tests with mvn test.
  6. Open student.db in DB Browser for SQLite to inspect the tables.
  7. Import the Postman collection. Set the three passwords in its variables, then run the folders in order (API.md, section 8).
Restarting the app creates new signing keys. All existing logins stop working, so log in again.
